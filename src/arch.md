# Проектирование схем коллекций данных и выбор стратегии шардирования

## Контекст

Онлайн-магазин «Мобильный мир» сильно вырос, и теперь там можно купить не только аксессуары для смартфонов, но также электронику, аудио- и бытовую технику и другие категории товаров. 

«Мобильный мир» хранит информацию о заказах, товарах и корзинах в трёх коллекциях в MongoDB. 

## Коллекция carts (Корзины)

```json
{
  "_id": "6a36e71b933ee74be9d1a7ba",
  "user_id": "usr_98765", 
  "session_id": "sess_abc123xyz",
  "status": "active",
  "items": [
    {
      "product_id": "prod_001",
      "quantity": 2
    },
    {
      "product_id": "prod_042",
      "quantity": 1
    }
  ],
  "created_at": "2026-06-20T19:16:01Z",
  "updated_at": "2026-06-20T23:15:00Z",
  "expires_at": "2026-06-21T23:15:00Z" 
}
```

### Основные операции
Частые гостевые сессии, получение активной корзины по сессии или ID пользователя, слияние корзин.

### Анализ потенциальных кандидатов для шард ключей

| Кандидат в ключ | Плюсы (➕) | Минусы (➖) | Вывод |
| :--- | :--- | :--- | :--- |
| **`{ session_id: "hashed" }`** | Есть у всех (и у гостей, и у авторизованных) с первой секунды. Идеально распределяет нагрузку на запись в распродажи. | При поиске *только* по `user_id` (редкий сценарий) роутер выполнит сканирование всего кластера. | **Оптимальный выбор** |
| **`{ user_id: "hashed" }`** | Мгновенно находит корзины авторизованных пользователей на одном конкретном шарде. | Гостевые корзины не имеют `user_id` (`null`). Все гости полетят на один шард, вызвав его перегрузку. | **Не подходит** |
| **`{ _id: "hashed" }`** | Равномерно распределяет документы по дискам. | Приложение не знает `_id` при поиске корзины. Любой запрос заставит роутер искать по всему кластеру. | **Не подходит** |

---

### Выбор стратегии и шард ключа

**Выбранная стратегия:** 
Шардирование на основе хэшированного ключа.

**Шард-ключ:** `{ session_id: "hashed" }`

**Обоснование:**

Корзины покупателей — это быстрорастущие и часто удаляемые данные. Поскольку на сайт заходит огромное количество неавторизованных гостей, хэширование уникального `session_id` позволяет идеально ровным слоем распределить операции записи по всем шардам кластера. 

Это полностью исключает риск перегрузки одного сервера в моменты пиковых распродаж, а роутер всегда точно знает, на какой шард отправить запрос на добавление товара в корзину.

## Коллекция products (Товары)

```json
{
  "_id": "prod_001",
  "name": "Смартфон X",
  "category": "Электроника",
  "price": 59990.00,
  "stock_by_geo": {
    "ekaterinburg": 50,
    "kaliningrad": 30,
    "moscow": 120
  },
  "attributes": {
    "color": "Черный",
    "size": "6.7 дюймов"
  }
}
```
### Основные операции
Поиск по категориям, фильтрация по цене, описание на странице продукта, обновление остатков.

### Анализ потенциальных кандидатов для шард ключей

| Кандидат в ключ | Плюсы (➕) | Минусы (➖) | Вывод |
| :--- | :--- | :--- | :--- |
| **`{ category: 1, _id: 1 }`** | Локализует данные. Товары одной категории лежат на одном шарде. Запросы каталога по категориям и цене выполняются быстро. | Популярные категории (например, «Смартфоны») нагружают свой шард сильнее остальных. | **Оптимальный выбор** |
| **`{ _id: "hashed" }`** | Отлично подходит для точечного обновления остатков товара и открытия карточки продукта по его ID. | Ломает поиск по категориям и ценам. Любой фильтр покупателя в каталоге заставит сканировать весь кластер. | **Не подходит** |

---

### Выбор стратегии и шард ключа

**Выбранная стратегия:** Шардирование по диапазону значений на основе составного ключа.

**Шард-ключ:** `{ category: 1, _id: 1 }`

**Обоснование:** 

Покупатели интернет-магазинов редко ищут товары хаотично — они заходят в конкретные разделы (например, «Бытовая техника» или «Электроника») и настраивают фильтр цен. 

Данная стратегия группирует товары одной категории внутри одного шарда. Благодаря этому роутер `mongos` при поиске в каталоге направляет запрос целенаправленно на один сервер, а не опрашивает весь кластер, что критически экономит ресурсы системы. <br>
Второе поле `_id` гарантирует высокую уникальность ключа.

## Коллекция orders (Заказы)

```json
{
  "_id": "ord_11223344",
  "user_id": "usr_98765",
  "created_at": "2026-06-20T23:18:00Z",
  "items": [
    {
      "product_id": "prod_001",
      "price_at_purchase": 59990.00,
      "quantity": 1
    }
  ],
  "status": "created",
  "total_amount": 59990.00,
  "geo_zone": "moscow"
}
```
### Основные операции
Быстрое создание заказов со списанием остатков, просмотр истории покупок в личном кабинете

### Анализ потенциальных кандидатов для шард ключей

| Кандидат в ключ | Плюсы (➕) | Минусы (➖) | Вывод |
| :--- | :--- | :--- | :--- |
| **`{ user_id: "hashed" }`** | История заказов одного клиента лежит на одном шарде. Запрос истории покупок выполняется мгновенно без поиска по всему кластеру. | Поиск заказов аналитиками по геозонам потребует сканирования всех шардов кластера. | **Оптимальный выбор** |
| **`{ geo_zone: 1 }`** | Удобно для локальной логистики складов по конкретным городам. | Крайне неравномерная нагрузка. Крупные города (Москва) заберут 80% трафика, переполнив один шард. | **Не подходит** |
| **`{ created_at: 1 }`** | Удобно для выгрузки ежедневных бухгалтерских отчетов. | Эффект «горячего шарда». Все новые заказы реального времени будут записываться строго на один текущий шард. | **Не подходит** |

---

### Выбор стратегии и шард ключа

**Выбранная стратегия:** Локализованная по пользователю стратегия с хэшированием.

**Шард-ключ:** `{ user_id: "hashed" }`

**Обоснование:** 

Самая частая операция для этой коллекции после покупки — отображение истории заказов в личном кабинете клиента. <br>
Выбор `user_id` в качестве шард-ключа гарантирует, что все прошлые покупки конкретного человека будут лежать в одном месте. Приложение достанет историю покупок за миллисекунды. 

Хэширование ключа необходимо для того, чтобы заказы разных пользователей распределялись по серверам параллельно и равномерно, предотвращая появление «горячих» шардов.

## Примеры команд MongoDB для настройки и проверки шардирования

Перед включением шардирования для коллекций необходимо обязательно активировать шардирование для самой базы данных `somedb` и создать нужные индексы на первичных шардах.

### Подготовка базы данных и создание индексов

Эти команды выполняются через роутер `mongos`:

```javascript
use somedb;

sh.enableSharding("somedb");

db.carts.createIndex({ "session_id": "hashed" });

db.products.createIndex({ "category": 1, "_id": 1 });

db.orders.createIndex({ "user_id": "hashed" });
```

### Команды применения стратегий шардирования

После создания индексов запускаем процесс распределения коллекций по выбранным шард-ключам:

```javascript
sh.shardCollection("somedb.carts", { "session_id": "hashed" });

sh.shardCollection("somedb.products", { "category": 1, "_id": 1 });

sh.shardCollection("somedb.orders", { "user_id": "hashed" });
```

### Команды для проверки работы кластера

Эти команды нужны чтобы убедиться, что данные разлетаются по серверам правильно:

```javascript
sh.status();

db.carts.getShardDistribution();
db.products.getShardDistribution();
db.orders.getShardDistribution();

db.adminCommand({ listShards: 1 });
```

# Выявление и устранение «горячих» шардов

## Контекст

В процессе эксплуатации онлайн-магазина «Мобильный мир» было выявлено появление «горячего» шарда. Из-за высокой популярности категории «Электроника» на один из узлов легло более 70% всех поисковых и транзакционных запросов. 

Ниже представлена стратегия мониторинга, автоматического перераспределения данных и изменения архитектуры ключей для предотвращения подобных инцидентов.

---

## Метрики мониторинга состояния шардов

Для раннего выявления дисбаланса нагрузки необходимо настроить сбор следующих ключевых метрик на каждом шарде кластера:

### Метрики производительности (Инфраструктурные)
*   **CPU Utilization (по каждому узлу):** Рост утилизации процессора выше 80% на одном шарде при простое остальных — главный признак «горячего» узла.
*   **Disk IOPS / Очередь диска (Disk Queue Length):** Показывает, справляется ли дисковая подсистема шарда с потоком записи и чтения.
*   **Network Traffic (In/Out):** Избыточный сетевой трафик на конкретном узле сигнализирует о массовом скачивании тяжелых документов (например, картинок или описаний электроники).

### Метрики MongoDB (Системные)
*   **Распределение чанков (Chunk Distribution):** Разница в количестве чанков (кусков данных) между шардами.
*   **Количество операций (Opcounter):** Аномально высокое количество операций `query` (чтения) и `update/insert` (записи) на одном шарде по сравнению с другими.
*   **Размер данных (Data Size per Shard):** Физический объем данных коллекции на каждом диске.

---

## Механизмы устранения дисбаланса и автоматического распределения

Для борьбы с «горячими» шардами в кластере можно использовать двухэтапный подход: автоматическое фоновое выравнивание кластера и ручное экстренное вмешательство администратора при критических пиках нагрузки.

### Автоматические механизмы перераспределения (Фоновые)
1. **Автоматическое расщепление чанков:** Роутер `mongos` постоянно следит за размером кусков данных (чанков). Как только размер чанка с категорией «Электроника» превышает лимит (по умолчанию 64 МБ), система сама делит его пополам без участия человека.
2. **Автоматическая балансировка:** Фоновый процесс Балансировщик (`Balancer`) постоянно считает чанки на серверах. Если на Шарде-1 их стало сильно больше, чем на Шарде-2, автоматика сама начинает миграцию данных на свободный узел.

### Б. Ручные механизмы устранения (Экстренные)
1. **Настройка окна балансировки:** Если перенос данных днем тормозит сайт, администратор настраивает автоматику так, чтобы она двигала файлы строго ночью.
2. **Принудительное разделение тяжелых чанков:** Если чанк с электроникой вырос слишком быстро и заблокировался, администратор вручную режет его по ID товаров.
3. **Шардирование по зонам:** Администратор может жестко приказать системе: *«Выделить под категорию „Электроника“ отдельный самый мощный сервер (Zone), а остальные товары оставить на других нодах»*.

## Примеры команд и настроек MongoDB

Все команды выполняются через роутер `mongos`.

### Проверка текущего дисбаланса и распределения чанков

Перед началом работ необходимо оценить масштаб проблемы:

```javascript
use somedb;
db.products.getShardDistribution();

sh.getBalancerState();
```

### Команды MongoDB для настройки автоматического перераспределения

Все команды выполняются через роутер `mongos`:

```javascript
use config;

db.settings.updateOne(
   { _id: "autosplit" },
   { \$set: { enabled: true } },
   { upsert: true }
);

sh.startBalancer();
sh.enableBalancing("somedb.products");

db.settings.updateOne(
   { _id: "chunksize" },
   { \$set: { value: 16 } },
   { upsert: true }
);

sh.getBalancerState();
```


### Настройка расписания (окна) работы балансировщика

Ограничим работу балансировщика ночным временем (например, с 02:00 до 06:00), чтобы он не создавал нагрузку на диски во время дневного пика продаж:

```javascript

use config;
db.settings.updateOne(
   { _id: "balancer" },
   { \$set: { activeWindow: { start: "02:00", stop: "06:00" } } },
   { upsert: true }
);
```

### Ручное разделение перегруженного чанка 
Если чанк с категорией «Электроника» заблокирован и не может переехать автоматически, делим его по конкретному ID товара:

```javascript
sh.splitAt(
   "somedb.products",
   { category: "Электроника", _id: ObjectId("6a36e71b933ee74be9d1a7ba") }
);
```

### Настройка зон для популярной категории

Принудительно заставим MongoDB отправлять всю «Электронику» на специально подготовленный мощный `shard2_set`:

```javascript
sh.addShardToZone("shard2_set", "POWER_ZONE");

sh.updateZoneKeyRange(
   "somedb.products",
   { category: "Электроника", _id: MinKey },
   { category: "Электроника", _id: MaxKey },
   "POWER_ZONE"
);
```

# Настройка чтения с реплик и консистентность

## Контекст
Для оптимизации нагрузки на кластер MongoDB онлайн-магазина «Мобильный мир» настроена стратегия распределения запросов чтения. Тяжелые и некритичные к задержкам запросы перенаправляются на вторичные реплики (`secondary`), а операции, требующие абсолютной точности данных, выполняются строго на главной ноде (`primary`).

---

## Таблица распределения операций чтения

| Коллекция | Операция чтения | Точка чтения (Primary / Secondary) | Допустимая задержка репликации |
| :--- | :--- | :--- | :--- |
| **`products`** | Просмотр карточки товара (описание, цвет, размер) | **Secondary**  | до 5-10 минут |
| **`products`** | Поиск товаров по категориям и фильтрация по ценам | **Secondary** | до 1-2 минут |
| **`products`** | Проверка остатков в геозоне при оформлении заказа | **Primary** | **0 секунд** (Строгая консистентность) |
| **`orders`** | Отображение статуса заказа в личном кабинете | **Secondary** | до 5-10 секунд |
| **`orders`** | Поиск истории заказов конкретного пользователя | **Secondary**  | до 30 секунд |
| **`carts`** | Получение текущей активной корзины пользователя/гостя | **Primary**  | **0 секунд** (Строгая консистентность) |

---

## Обоснование выбора и бизнес-логика

### Коллекция `products` (Товары)
*   **Чтение с Secondary (Карточка и поиск):** Описание товара, его цвет, размер и базовая цена меняются контент-менеджерами редко (низкая частота обновлений). Если покупатель во Владивостоке увидит новое описание смартфона на 5 минут позже, чем оно обновилось в Москве, это никак не повлияет на бизнес-логику.
*   **Чтение с Primary (Остатки на складах):** Проверка количества товара в геозоне перед списанием — критически важная операция. Если читать остатки со старой реплики (даже с задержкой в 2 секунды), возникнет риск продажи товара, которого физически уже нет на складе. Это приведет к недовольству клиентов, отменам заказов и финансовым убыткам.

### Коллекция `orders` (Заказы)
*   **Чтение с Secondary (История и статусы):** Запросы к истории покупок создают высокую нагрузку на чтение, но не требуют моментальной точности. Допустима задержка репликации в несколько секунд. Если пользователь нажал кнопку «Оплатить», и в личном кабинете статус заказа сменился с *«Создан»* на *«Оплачен»* не мгновенно, а через 5 секунд — это нормальное и ожидаемое поведение для крупного интернет-магазина.

### Коллекция `carts` (Корзины)
*   **Чтение строго с Primary:** Корзина — это динамический объект с высочайшей частотой обновлений. Покупатель может кликать по кнопкам, быстро добавляя чехол, меняя количество товаров с 1 на 2 и удаляя лишнее. Если направить чтение на `secondary` с задержкой, возникнет «эффект мерцания»: пользователь добавляет товар, страница обновляется, а товар пропадает, так как реплика еще не успела обновиться. Корзина всегда должна быть строго консистентной.

# Миграция на Cassandra: модель данных, стратегии репликации и шардирования

## Контекст
Во время «чёрной пятницы» интернет-магазин использовал MongoDB с шардированием на основе диапазонов (Range-Based Sharding). При резком увеличении нагрузки (50 000 запросов/сек.) возникла высокая задержка при масштабировании:

При добавлении новых шардов MongoDB полностью перераспределяла данные между всеми узлами, что вызывало просадку latency в пик нагрузки, так как система тратила ресурсы на перемещение данных.

Руководство решило перейти на БД Cassandra, чтобы обеспечить:
* Высокую отказоустойчивость (leaderless‑репликация).
* Быстрое горизонтальное масштабирование без полного перераспределения данных.
* Равномерное распределение данных.

## Определение критичности данных и целесообразности миграции на Apache Cassandra

При переходе с MongoDB на Apache Cassandra необходимо четко разделить данные. Cassandra жертвует строгой транзакционностью ради бесконечного масштабирования и мгновенной записи. 

Ниже приведена классификация данных по их критичности и детальное обоснование, для каких именно сущностей внедрение Cassandra принесет бизнесу максимальную выгоду.

---

### Оценка данных с точки зрения целостности и скорости обработки

#### Данные, критичные к целостности
Для этих сущностей малейшая рассинхронизация между серверами означает прямые финансовые потери, юридические риски и сбои в логистике.

*   **Текущие остатки товаров (`products.stock_by_geo`):** Требуют абсолютной точности. Если из-за задержки репликации два клиента одновременно купят последний доступный на складе в Екатеринбурге смартфон, возникнет оверселлинг. Это приведет к отменам заказов и негативу.
*   **Финансовые транзакции и статусы оплаты заказов:** Сумма к оплате, факт списания денег и финальный статус («Оплачено») не могут быть «примерными» или обновиться «чуть позже». Здесь необходима строгая консистентность.

#### Данные, критичные к скорости обработки
Эти данные генерируют основной поток из 50 000 запросов/сек во время «Черной пятницы». Для них важнее, чтобы сайт оставался доступным и мгновенно реагировал на клики, а задержка синхронизации в 1–2 секунды не является проблемой.

*   **Активные корзины и гостевые сессии (`carts`):** Каждую секунду тысячи людей добавляют, удаляют и меняют количество товаров. База должна записывать эти действия мгновенно.
*   **Поток создания новых заказов (`orders`):** В пик распродажи система должна максимально быстро зафиксировать намерение пользователя купить товар («положить заказ в очередь»), чтобы клиент не видел экран долгой загрузки.
*   **История заказов (Архив):** Генерирует огромный поток запросов на чтение в личных кабинетах, но сами данные никогда не меняются (только добавляются).

### Для каких данных применение Cassandra имеет смысл

Apache Cassandra идеально подходит для **высоконагруженных, геораспределенных и быстрорастущих данных**, где бизнес готов временно пожертвовать строгой консистентностью ради того, чтобы сайт гарантированно выдержал 50 000 запросов/сек.

#### Смысл внедрения Cassandra очевиден для следующих данных:

1.  **Активные корзины и пользовательские сессии (`carts`)**
    *   **Скорость записи:** Архитектура Cassandra оптимизирована под сверхбыструю запись. Она проглотит поток корзин в «Черную пятницу» без блокировок таблиц.
    *   **Масштабируемость без перегрузок:** В отличие от MongoDB, которая при добавлении шардов начинает двигать данные по сети и тормозить, Cassandra использует **согласованное хэширование**. При добавлении нового узла в кольцо, данные переносятся только с соседних серверов, не затрагивая весь кластер. Нагрузка на сеть минимальна.
2.  **Создание заказов и история покупок (`orders`)**
    *   **Геораспределенность:** Cassandra из коробки поддерживает работу с несколькими дата-центрами. Заказ покупателя из Владивостока мгновенно запишется в локальный дальневосточный узел, а затем фоном синхронизируется с Москвой. Пользователь получит минимальный пинг.
    *   **Равномерность распределения:** За счет хэширования ключа партиционирования заказы миллионов пользователей равномерно размажутся по всему кольцу серверов. Эффект «горячего шарда» исключен.

#### Для каких данных применять Cassandra нужно с осторожностью:

*   **Каталог товаров и остатки (`products`)**
    *   Cassandra плохо подходит для поиска с динамическими фильтрами (выбор диапазона цен внутри категории электроники), так как она требует строгого проектирования таблиц под конкретные запросы.
    *   Для контроля остатков (`stock_by_geo`) придется использовать уровень консистентности `QUORUM` для чтений и записей. Это снизит скорость работы Cassandra, но обеспечит необходимую целостность для защиты от оверселлинга.

#### Итоговый вывод

Перевод **корзин, сессий и процесса регистрации заказов** на Cassandra полностью решает проблему «Черной пятницы». Сайт перестанет падать при масштабировании, так как Cassandra будет равномерно распределять эти тяжелые потоки данных по кольцу серверов без полной перетряски кластера.

## Схемы таблиц и обоснование выбора ключей

### Таблица `carts_by_session` (Корзины)
*   **Основной запрос:** Получение активной корзины по фильтру `session_id` или `user_id`.
*   **Структура Primary Key:** `PRIMARY KEY ((session_id), item_id)`
*   **Обоснование выбора Partition Key (`session_id`):** 
<br> Идентификатор сессии (`session_id`) уникален для каждого посетителя сайта (и для гостей, и для авторизованных). Cassandra берет хэш от этого значения и равномерно «размазывает» корзины по всем узлам виртуального кольца. 
<br> В «Черную пятницу» нагрузка от 50 000 гостей распределится идеально поровну, полностью исключая перегрузку одного сервера.

*   **Обоснование выбора Clustering Key (`item_id`):** 
<br> Позволяет хранить несколько товаров внутри одной корзины. <br> Все товары конкретного покупателя физически записываются на жестком диске строго друг за другом в один ряд. Когда пользователь открывает корзину, Cassandra считывает весь список товаров за одну операцию последовательного чтения (Sequential I/O). <br> Это гарантирует минимальный пинг и мгновенный отклик интерфейса.

```sql
CREATE TABLE sharding_repl_cache.carts_by_session (
    session_id text,       -- Partition Key (Клич партиционирования)
    item_id text,          -- Clustering Key (Кластерный ключ для сортировки)
    user_id text,
    product_id text,
    quantity int,
    status text,
    created_at timestamp,
    updated_at timestamp,
    PRIMARY KEY ((session_id), item_id)
);
```

### Таблица `orders_by_user` (История заказов)
*   **Основной запрос:** Быстрый поиск истории заказов конкретного пользователя с сортировкой от новых к старым.
*   **Структура Primary Key:** `PRIMARY KEY ((user_id), order_id)` c сортировкой `WITH CLUSTERING ORDER BY (order_id DESC)`
*   **Обоснование выбора Partition Key (`user_id`):** 
Самая частая и тяжелая операция для этой таблицы — просмотр истории покупок в личном кабинете. Сделав `user_id` ключом партиционирования, мы гарантируем, что **абсолютно все заказы конкретного человека будут физически лежать на одном сервере**. Роутеру базы данных не нужно опрашивать весь кластер, он идет точечно на один узел.
*  **Обоснование выбора Clustering Key (`order_id`):** 
Использование специального типа `timeuuid` (содержит в себе время создания) в качестве кластерного ключа позволяет автоматически сортировать заказы на диске. <br> Благодаря настройке `WITH CLUSTERING ORDER BY (order_id DESC)`, новые заказы физически дописываются в начало файла. <br> Приложение всегда мгновенно получает список покупок от самых свежих к старым без затрат ресурсов процессора на сортировку.

```sql
CREATE TABLE sharding_repl_cache.orders_by_user (
    user_id text,          -- Partition Key (Клич партиционирования)
    order_id timeuuid,     -- Clustering Key (Сортировка по времени создания заказа)
    geo_zone text,
    status text,
    total_amount decimal,
    items_list text,
    PRIMARY KEY ((user_id), order_id)
) WITH CLUSTERING ORDER BY (order_id DESC);
```

### Таблица `products_by_category` (Каталог товаров)
*   **Основной запрос:** Поиск товаров по категориям и фильтрация/сортировка по диапазону цен.
*   **Структура Primary Key:** `PRIMARY KEY ((category), price, product_id)`
*   **Обоснование выбора Partition Key (`category`, `bucket_id`):** 
Запросы покупателей в каталоге всегда привязаны к разделам сайта (например, «Электроника» или «Бытовая техника»). Группировка товаров по категориям на конкретных серверах позволяет локализовать тяжелые поисковые запросы. 
<br> Однако, учитывая специфику «Чёрной пятницы», категория «Электроника» генерирует 70% трафика и может перегрузить один узел. Чтобы этого избежать, в ключ партиционирования добавлено второе поле — **`bucket_id`** (случайное число от 1 до 5). Это превращает ключ в составной (`Composite Partition Key`). Благодаря этому сверхпопулярная «Электроника» принудительно разрезается базой данных на 5 мелких независимых частей и разносится по разным серверам кластера, гарантируя равномерную нагрузку.


*   **Обоснование выбора Clustering Key (`price`, `product_id`):** 
<br> Первое поле кластерного ключа (`price`) физически сортирует товары на диске по стоимости. Это позволяет базе данных мгновенно отдавать результаты для самых популярных фильтров сайта (например, *«Показать электронику в диапазоне цен от 10 000 до 30 000 рублей»*) с помощью быстрого сканирования диапазона строк на диске. 
<br> Второе поле (`product_id`) добавлено для обеспечения уникальности первичного ключа строки.

```sql
CREATE TABLE sharding_repl_cache.products_by_category (
    category text,         -- Partition Key (Ключ партиционирования)
    bucket_id int,         -- Часть Partition Key (случайное число от 1 до 5)
    price decimal,         -- Clustering Key 1 (Для фильтрации по диапазону цен)
    product_id text,       -- Clustering Key 2 (Для уникальности строки)
    name text,
    stock_by_geo map<text, int>, 
    attributes map<text, text>,
    PRIMARY KEY ((category, bucket_id), price, product_id)
);
```

## Обоснование модели: защита от «горячих» партиций и минимизация влияния решардинга

При экстремальной нагрузке в 50 000 запросов/сек классические базы данных часто сталкиваются с двумя проблемами: перегрузкой отдельных узлов («горячие» партиции) и падением скорости работы сайта при добавлении новых серверов (тяжелый решардинг). Спроектированная концептуальная модель в Apache Cassandra успешно решает обе эти проблемы на уровне архитектуры.

### Защита от «горячих» партиций

«Горячая» партиция возникает, когда огромное количество запросов от покупателей летит в одну точку кластера, перегружая процессор и диски конкретного сервера.

1. **Равномерность для корзин и сессий (`carts_by_session`):** 
   Поскольку ключом партиционирования выбран `session_id`, данные миллионов посетителей перемешиваются алгоритмом хэширования. Каждый пользователь получает свой случайный токен и отправляется на свой узел. Нагрузка распределяется по кластеру идеально ровным слоем, исключая появление «горячего» сервера.
2. **Равномерность для заказов (`orders_by_user`):** 
   Шардирование по `user_id` гарантирует, что в пик распродаж новые заказы от тысяч разных людей будут записываться на разные серверы параллельно. 
3. **Защита каталога товаров (`products_by_category`):** 
   В ТЗ указано, что категория «Электроника» создает 70% трафика и способна вызвать появление «горячей» партиции. Для предотвращения этой ситуации в модели заложена стратегия **составного Partition Key со случайным бакетированием**:
   * Вместо простого ключа `category` применяется составной ключ `((category, bucket_id))`.
   * Поле `bucket_id` — это случайное число от 1 до 5, которое автоматически присваивается товарам при записи.
   * *Результат:* Сверхпопулярная категория «Электроника» автоматически разрезается базой данных на 5 мелких изолированных под-партиций и физически разносится на разные серверы кластера. Это полностью ликвидирует перекос нагрузки.

### Минимизация влияния решардинга при изменении топологии кластера

Главная причина, почему интернет-магазин отказался от MongoDB во время «Черной пятницы» — это просадка скорости (latency) сайта при добавлении новых серверов. MongoDB на основе Range-Based шардинга была вынуждена полностью перетряхивать карту кластера и двигать огромные объемы данных между всеми узлами одновременно, забивая сеть и диски.

Apache Cassandra решает эту проблему с помощью **Согласованного хэширования (Consistent Hashing)** и виртуального кольца токенов:

1. **Локальный перенос данных:** 
   Все серверы Cassandra выстроены в виртуальное кольцо, где каждый узел отвечает за свой строгий диапазон хэш-чисел.
2. **Эффект добавления нового сервера:** 
   Когда в разгар «Черной пятницы» мы добавляем в кластер новый сервер для масштабирования, он не вызывает глобального пересчета всей базы. Новый узел встраивается в конкретную точку кольца и забирает себе лишь **часть данных у своих ближайших соседей**.
3. **Нулевой простой системы:** 
   Данные начинают плавно и незаметно копироваться только с соседних серверов на новый. Остальные 80–90% узлов кластера даже не замечают изменения топологии — они продолжают обслуживать покупателей на максимальной скорости. 

В системе полностью отсутствует понятие «глобального решардинга», что гарантирует стабильно низкий latency и бесперебойную работу онлайн-магазина при горизонтальном расширении в моменты пиковых нагрузок.

## Выбор стратегии обеспечения целостности данных

Для минимизации задержек и обеспечения надежности в leaderless-архитектуре Кассандры используются три стандартных механизма восстановления данных: **Hinted Handoff**, **Read Repair** и **Anti-Entropy Node Repair**.

###  Анализ механизмов и их компромиссы

1.  **Hinted Handoff:**
    *   *Как работает:* Если во время записи заказа один из узлов-копий временно выключился (или моргнула сеть), узел-координатор сохраняет эту запись у себя в виде подсказки (hint). Как только потерянный узел возвращается в сеть, координатор сразу пересылает ему все пропущенные данные.
    *   *Компромисс:* **Минимальный latency**. Этот процесс работает полностью в фоновом режиме и вообще не тормозит запросы покупателей во время «Черной пятницы».
    *   *Уровень гарантии:* Низкий. Помогает только при кратковременных сбоях (по умолчанию подсказки хранятся всего 3 часа).

2.  **Read Repair (Восстановление при чтении):**
    *   *Как работает:* Когда приложение запрашивает данные с уровнем консистентности `QUORUM`, Cassandra читает данные с нескольких узлов. Если система замечает, что на одном сервере лежит старая версия корзины, а на другом — новая, она возвращает приложению свежую версию, а в фоновом режиме автоматически досылает обновление на отставший сервер.
    *   *Компромисс:* **Средний latency**. На чтение тратится чуть больше сетевых ресурсов для сравнения контрольных сумм.
    *   *Уровень гарантии:* Высокий для часто читаемых данных.

3.  **Anti-Entropy Repair (Глобальный ремонт / Node Tool Repair):**
    *   *Как работает:* Тяжелая системная утилита, которая запускается администратором по расписанию. Серверы сравнивают терабайты своих данных с помощью математических *деревьев Меркла* (Merkle Trees) и принудительно синхронизируют всё, что сломалось или отстало за долгое время.
    *   *Компромисс:* **Высокий latency и тяжелая нагрузка на диски**. Запускать этот процесс во время распродажи категорически запрещено.
    *   *Уровень гарантии:* Максимальный. Гарантирует 100% устранение любых расхождений в долгосрочной перспективе.

### Распределение стратегий по сущностям интернет-магазина

| Сущность / Таблица | Приоритетная стратегия | Обоснование выбора и компромиссы |
| :--- | :--- | :--- |
| **`carts_by_session`** (Корзины) | **Hinted Handoff** + **Read Repair** | *Низкий latency важнее строгой точности.* Корзины меняются каждую секунду. Если из-за сбоя одна нода отстанет на полсекунды, фоновый `Read Repair` или `Hinted Handoff` быстро и незаметно дошлет данные при следующем клике пользователя. Риска для денег бизнеса тут нет, а скорость работы корзины в «Черную пятницу» должна быть максимальной. |
| **`orders_by_user`** (Заказы и оплата) | **Anti-Entropy Repair** (Ночной запуск) | *Высокая целостность важнее latency.* Финансовые статусы заказов не могут быть «примерными». Чтобы гарантировать, что ни один оплаченный заказ не потеряется из-за долгого падения какого-то сервера, раз в неделю (в часы минимального трафика) должен запускаться принудительный глобальный ремонт кластера. |
| **`products_by_category`** (Остатки товаров) | **Read Repair** (Агрессивный) | *Баланс скорости и точности.* Проверка остатков электроники перед покупкой должна быть точной. Поскольку каталог товаров читается миллионы раз в день, агрессивный `Read Repair` будет автоматически «лечить» и обновлять остатки на отставших репликах при каждом поисковом запросе клиентов, не дожидаясь ночных проверок. |
